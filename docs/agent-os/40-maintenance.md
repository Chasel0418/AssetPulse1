# 40 — 維護協議：怎麼安全地更新這套制度

觸發：要修改 CLAUDE.md 或 `docs/agent-os/` 任何檔案之前，先讀完本檔。

## 1. 權限分級

**可以自行改（不必問使用者）：**
- `LESSONS.md`：新增教訓（append-only，見 §3）。
- `10-dispatch.md` §7 工具速查表：新增或修正確認過的工具名。
- CLAUDE.md「本 repo 現況」一節：補建置/測試指令等**事實性**內容。
- 明確的事實錯誤（工具名打錯、路徑失效）：直接修，commit message 說明
  原值、新值、驗證方式。

**先問使用者再改：**
- 任何**規則本身**：硬規則、升降級門檻、模板結構、判準的增刪改。
  就算你確信規則錯了，也是「帶著證據提案」而不是直接改——證據格式：
  規則原文、實際發生什麼、你建議改成什麼。
- 刪除任何檔案或整個章節。
- `.claude/agents/` 與 `.claude/settings.json`（影響所有未來 session 的行為）。

**永遠不做：**
- 為了讓當前任務好過而放寬規則（例如「這次先跳過驗收」）。規則擋住你，
  多半代表任務有問題，見 `20-judgment.md` §4。

## 2. 改法（機械步驟）

1. 備份：`cp <檔案> <檔案>.bak-<YYYYMMDD>`（同目錄）。合併 PR 前保留，
   git 歷史穩定後可刪 .bak。
2. 用 Edit 做最小修改，不要整檔重寫（整檔重寫需使用者同意）。
3. Read 回改動段落，確認語意沒被改壞、沒和其他檔矛盾
   （快速檢查法：grep 其他檔對這條規則的引用）。
4. commit（message 寫「改了什麼＋為什麼」）並 push。

## 3. 教訓寫回：LESSONS.md

踩到坑（工具行為與預期不符、環境陷阱、規則沒覆蓋的情況）→ 當次就寫，
不要想「等等再記」——session 結束就沒有等等了。

格式（append 到檔尾，一條 3–5 行）：

```
## YYYY-MM-DD <一句話標題>
情境：做什麼時遇到的。
坑：實際發生什麼（附錯誤訊息關鍵句）。
解法/繞法：怎麼過的，或確認過不去。
建議：（可選）哪條規則該補充——不要直接改規則，寫在這裡等使用者裁決。
```

判準：**未來 session 遇到同樣情況會不會少走 10 分鐘彎路？會 → 記；
只是這次任務的細節 → 不記。**

## 4. 精簡週期

- `LESSONS.md` 超過 **30 條**或 **300 行**：向使用者提案精簡——把已升格
  為正式規則的刪掉、同類合併、過時的標 deprecated。精簡本身要使用者同意。
- CLAUDE.md 超過 **80 行**：代表有內容該下放到 `docs/agent-os/`，提案搬移。
- 每次精簡前整檔備份到 `docs/agent-os/archive/<檔名>-<YYYYMMDD>.md`。

## 5. 一致性守則

- 同一條規則只在一個檔案裡有**正文**，其他地方用「見 `<檔>#<節>`」引用。
  發現兩處正文不一致：以 `00-diagnosis.md` 的診斷意圖為準修正，並回報使用者。
- 新增檔案要同步更新 CLAUDE.md 路由表，否則等於不存在。
