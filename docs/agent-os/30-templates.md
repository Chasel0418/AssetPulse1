# 30 — 派工 prompt 模板

觸發：要派 subagent 時，選對應模板，填空後直接當 Agent tool 的 `prompt`。
`【】`是填空。共通規則：subagent 冷啟動，對話裡談過的背景**必須**重新寫進去；
範圍邊界與「不要做什麼」必填。model 選型見 `10-dispatch.md` §3。

---

## T1 搜尋／定位（subagent_type: Explore；model: haiku，範圍大或命名混亂用 sonnet）

```
目標：找出【要找的東西，例：使用者驗證邏輯的定義與所有呼叫點】。
動機：【為什麼要找，例：我要改它的回傳格式，需要知道影響面】。
範圍：【目錄/檔案範圍，例：src/ 之下；排除 tests/ 與 generated/】。
搜尋廣度：【medium / very thorough】。
驗收條件：每個結果給 檔案路徑:行號 與一句「這裡是什麼」；如果找不到，
列出你搜過的 pattern 與目錄，不要只回「沒找到」。
回報格式：≤15 行清單。不要貼程式碼原文，不要描述搜尋過程。
```

## T2 實作（subagent_type: general-purpose；model: sonnet）

```
目標：【做什麼，例：在 X 模組加入 Y 功能】。
動機：【為什麼，最終要支撐什麼使用情境】。
背景（你是冷啟動，以下是你需要知道的全部）：
- 【相關檔案與現況，例：入口在 src/a.py:120，現有類似實作在 src/b.py:45 可仿照】
- 【已做的決定，例：格式已定為 snake_case，不要重開這個問題】
範圍邊界：只改【檔案/目錄清單】；不要動【例：公開 API 簽名、CI 設定】；
不要 commit（由主對話統一 commit）。
驗收條件：
1. 【可執行的驗證，例：`pytest tests/test_y.py` 全綠】
2. 【行為驗證，例：實跑 `python -m x --y` 輸出包含 Z】
3. 程式風格與周圍程式碼一致（命名、註解密度）。
回報格式：改了哪些檔（路徑:行號區間）、每個驗收條件的結果與指令輸出摘要
（≤5 行）、你做過的假設。全文 ≤20 行。
```

## T3 重構／批次改檔（subagent_type: general-purpose；model: sonnet，模式已定型可用 haiku）

```
目標：把【模式 A】改成【模式 B】，套用到【範圍】。
動機：【例：A 已棄用；先前已在 src/c.py:30 手工改過一處，那是標準範例】。
標準範例：改法完全比照【檔案:行號】的做法。遇到不符合模式的變體
**不要自行發揮**，跳過並在回報中列出。
範圍邊界：只做這一種轉換，順手看到的其他問題記下來回報，不要修。
驗收條件：
1. 【機械可驗，例：`grep -rn "舊模式" src/` 回傳 0 筆，跳過清單裡的除外】
2. 【`<測試指令>` 通過】
回報格式：改動檔案數、跳過清單（路徑:行號＋為何不符模式）、測試結果。≤15 行。
```

## T4 研究／查證（subagent_type: general-purpose；查 Claude Code/API 用 claude-code-guide；model: sonnet）

```
問題：【要回答什麼，越具體越好，例：X 套件 v2 的 Y API 是否支援 Z，語法為何】。
動機：【答案會用來做什麼決定】。
來源優先序：【例：官方文件 > repo 內既有用法 > 其他】。禁止憑訓練記憶回答
版本相關問題，必須查到來源。
驗收條件：每個結論附來源（URL 或 檔案:行號）；查不到的明確標 UNCONFIRMED；
區分「文件說的」與「你推論的」。
回報格式：結論先行（≤5 行），證據清單在後。長篇整理寫到
【scratchpad 路徑】，回報只給路徑＋摘要。
```

## T5 審查／驗收（subagent_type: verifier；高風險時 model 覆寫 opus）

```
你要驗收的產出：【檔案路徑清單 / PR 編號 / 指令】。
任務背景（一句話）：【產出宣稱達成什麼】。
驗收條件（逐條判定 PASS/FAIL/UNVERIFIABLE）：
1. 【…】
2. 【…】
可用的驗證手段：【例：跑 pytest、實跑某指令、read-back 某檔】。
注意：不要求你判斷做法好不好，只判定是否符合上列條件；但驗收條件沒涵蓋
而你看到的風險，最後列出（≤3 條）。
```

---

## 派工後，主對話的收尾動作（每次都做）

1. 回報超出約定長度／貼了大段原文 → 摘要後丟棄原文，不要整段帶著走。
2. 回報裡的 UNCONFIRMED → 決定：再查、問使用者、或接受並記錄假設。
3. 失敗 → 按 `10-dispatch.md` §5 升降級，升級必附完整失敗軌跡。
4. 多個 subagent 的結論互相矛盾 → 不要自己硬裁，派 opus 當評審或問使用者。
